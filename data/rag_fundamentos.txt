Retrieval-Augmented Generation (RAG) es una arquitectura que combina un sistema de recuperación de información con un modelo de lenguaje generativo. La idea central es simple: en lugar de depender únicamente del conocimiento que el modelo aprendió durante su entrenamiento (que tiene una fecha de corte y puede no incluir información específica de un dominio), el sistema busca fragmentos de texto relevantes en una base de conocimiento externa y se los entrega al modelo como contexto antes de que genere la respuesta.

El flujo típico de un sistema RAG tiene dos fases claramente separadas. La primera es la fase de indexación (o ingesta), que se ejecuta una sola vez, o cada vez que la base de conocimiento cambia: los documentos se limpian, se dividen en fragmentos más pequeños llamados chunks, y cada chunk se convierte en un vector numérico (embedding) que se guarda en una base de datos vectorial junto con su texto original y su metadata. La segunda fase es la de consulta (o inferencia), que se ejecuta cada vez que un usuario hace una pregunta: la pregunta se convierte también en un embedding, se buscan los chunks más similares en la base vectorial, y esos chunks se insertan en un prompt junto con la pregunta original antes de pasárselo al modelo de lenguaje.

Las ventajas principales de RAG frente a depender solo del conocimiento paramétrico del modelo son tres. Primero, reduce las alucinaciones: el modelo tiene un contexto concreto de dónde sacar la respuesta, en lugar de inventar información. Segundo, permite citar la fuente exacta de donde salió cada dato, lo cual es clave en dominios donde la trazabilidad importa (legal, médico, soporte técnico). Tercero, permite actualizar el conocimiento del sistema simplemente agregando o modificando documentos en la base vectorial, sin necesidad de reentrenar ni hacer fine-tuning del modelo, que es un proceso mucho más costoso y lento.

Un punto crítico de robustez en cualquier sistema RAG es qué hacer cuando la búsqueda no encuentra contexto relevante para la pregunta del usuario. Un sistema mal diseñado le pasa igual esos chunks (aunque tengan baja similitud) al modelo, que termina generando una respuesta con apariencia de segura pero sin fundamento real, algo que se conoce como alucinación asistida por contexto irrelevante. Un sistema bien diseñado establece algún criterio de corte (por ejemplo, un umbral de distancia o similitud) y, si ningún chunk lo supera, responde explícitamente que no tiene información suficiente en su base de conocimiento en lugar de forzar una respuesta.

La arquitectura asíncrona es relevante en sistemas RAG de producción porque las dos operaciones más costosas del flujo de consulta -la búsqueda en la base vectorial y la llamada al modelo de lenguaje- son operaciones de entrada/salida (I/O): implican esperar una respuesta de un proceso externo (la base de datos o la API del proveedor del modelo). Usar funciones asíncronas (async/await) permite que, mientras se espera esa respuesta, el proceso no quede bloqueado y pueda seguir atendiendo otras solicitudes en paralelo, lo cual es fundamental cuando el sistema tiene que responder a múltiples usuarios al mismo tiempo.
